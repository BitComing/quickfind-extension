# QuickFind 代码优化评审

评审时间：2026-10-17
评审范围：`entrypoints/`（popup / options / content / background）、`shared/`、`build.mjs`、`wxt.config.ts`、`scripts/typecheck.mjs`
工作量基线：content/index.ts 3038 行 / 168 KB，options/main.ts 1686 行 / 108 KB，popup/main.ts 239 行，shared 4 文件 511 行；产物 content.js 122 KB（未压缩）

---

## 一、总体结论

工程质量在同类扩展中属于偏上：已有类型债务量化脚本 + 基线门禁、明确的构建兜底与校验、跨入口共享模块的先例（`search-actions.ts` / `note-drag.ts`）。真正的问题不在"没有规范"，而在**规范只覆盖了后来者，早先的三份实现没有被回收**。

按预期收益排序，前三位是：

1. **内容脚本的全局事件与 DOM 观察者过于昂贵**（`getPinnedSite()` 在每次 DOM 变动、每次滚动、每次页面输入、每次选区变化时都会执行一次完整 URL 解析）。这是唯一一类"用户在正常浏览网页、完全没碰 QuickFind 时就在付费"的开销，优先级最高。
2. **同一领域逻辑存在 2–3 份实现且已经产生行为分歧**（内置源迁移集合、默认组名、缩进像素、空态文案各不相同）。这是结构性风险：每次改需求都要改多处，且分歧已经在真实行为里出现了。
3. **`chrome.storage.sync` 单键 8 KB 配额与自定义图标（data URL）冲突，且保存失败不检查 `lastError`**。这是**静默丢配置**级别的缺陷，属于正确性问题而非风格问题。

另有两条需要单独确认的产品决策与已知缺陷，见第五节。

## 二、性能

### P1（高）每次 DOM 变动都执行一次完整的站点匹配

**证据**
- `entrypoints/content/index.ts:3031-3032`：`MutationObserver(schedulePinnedMount).observe(document.documentElement, { childList: true, subtree: true })`
- `entrypoints/content/index.ts:2612-2615`：`if (!getPinnedSite({ requireSearchResults: false }) || pinnedMountTimer) return;`

**问题**：守卫条件的求值顺序把最贵的调用放在了最前面。`pinnedMountTimer` 已经置位（防抖生效中）时，仍然会先执行一次 `getPinnedSite()`。而该函数（`1992-2039`）内含 10 余条正则匹配，未命中内置站点时还会落到 `getDynamicPinnedSites()`（`1952-1968`），后者对每个搜索源执行一次 `createTemplateSite()`（`1920-1950`，内部 `new URL` + 参数遍历）。

SPA 页面（微博、B 站、知乎）的 DOM mutation 频率可达每秒数百次，因此这是**每次 DOM 插入都跑一次十几到几十次 URL 解析**。这是本评审中量级最大的性能问题。

**建议**
```ts
function schedulePinnedMount() {
  if (pinnedMountTimer) return;                    // 先短路
  if (!getPinnedSite({ requireSearchResults: false })) return;
  pinnedMountTimer = window.setTimeout(() => { pinnedMountTimer = null; mountPinnedBar(); }, 120);
}
```
并进一步：在 `pinnedMountTimer` 生效期间不重复调用 `getPinnedSite()`，改为把"是否需要挂载"的判定合并进 `mountPinnedBar()` 内部（它本来就要算一次，`2581-2588`）。

**理由与收益**：改动约 3 行，语义完全等价（`mountPinnedBar` 内部已有同样的判定与早退），但把每 mutation 一次的昂贵调用降为每 120 ms 一次。在重度 SPA 上可消除绝大部分内容脚本的稳态 CPU 占用。

### P2（高）滚动、页面输入、选区变化三处高频监听各触发一次昂贵匹配

**证据**
- 滚动：`content/index.ts:3010-3011` 注册 `window scroll`(passive) 与 `document scroll`(capture)；处理函数 `refreshSelectionPosition`（`2985-3009`）第一句就是 `positionPinnedBar(getPinnedSite())`；而 `positionPinnedBar`（`2561-2578`）内又调用 `getPinnedEntries()`（`2562`），后者（`2101-2152`）会重建 `Map` 并多次线性扫描。
- 页面输入：`content/index.ts:2934-2938`，`document` 上 capture 的 `input` 监听，第一句是 `const site = getPinnedSite();`。**页面上任何一个输入框的每一次按键都会触发**。
- 选区：`2939-2954`（mouseup/touchend→`applySelectionToPinnedQuery` →`getPinnedSite()`+`findVisibleInput()`）、`2965-2970`、`2973-2976`（两条 `selectionchange`）。

**问题**：三处都没有合并到 rAF / 时间窗，且都在拿数据之前先做完整匹配。`findVisibleInput`（`2041-2048`）还会对候选输入框逐个 `getBoundingClientRect()` + `getComputedStyle()`，属强制布局。

**建议**
1. 滚动：`refreshSelectionPosition` 用 rAF 合并（同一帧内多次滚动只处理一次），并把 `positionPinnedBar` 需要的站点信息与条目列表**按 `location.href` 记忆化**：
   ```ts
   let pinnedCacheKey = '';
   let pinnedCacheSite = null;
   function getPinnedSiteCached() {
     if (pinnedCacheKey !== location.href) { pinnedCacheKey = location.href; pinnedCacheSite = getPinnedSite(); }
     return pinnedCacheSite;
   }
   ```
   `settings` 变化时清空缓存（现有 `storage.onChanged` 分支里加一行即可）。
2. `input` / `selectionchange`：把 `getPinnedSite()` 推迟到确认需要写值之后；或同样走缓存。
3. `findVisibleInput` 的可见性判定改用 `checkVisibility?.() ?? true` 快路径，仅在需要时回退到 `getComputedStyle`。

**理由与收益**：`getPinnedSite()` 的结果在一个 URL 生命周期内只取决于 `settings` 与 `location`，与滚动/输入无关，属于天然可缓存的纯计算。收益是让三类高频事件回到"只做几次属性比较"的成本；对滚动掉帧与输入延迟有直接改善（内存中已记录过真实站点上 `position:fixed` 含块变化导致浮层错位的坑，同一批代码路径）。

### P3（中）两处内联模板合计约 39 KB 的 HTML/CSS 在每次页面注入时解析

**证据**（实测字符数）
- `shadow.innerHTML`（`258-548`）：共 32 536 字符，其中 `<style>` 25 148 字符；其中 `.llm-dock` 段 6 394 字符，占模板 19.7%。
- `pinnedHost` 的 `root.innerHTML`（`2185-2227`）：6 818 字符，其中 `<style>` 5 918 字符。

**问题**：两个 shadow root 的样式各存一份、各自解析。且 `llmDockVisible` 默认 `false`（`content/index.ts:209`），但整个「随心问」面板（含 6.4 KB 标记与全部样式）仍随模板一起解析并常驻 DOM。

**建议**
1. 样式改为构建期字符串常量：把 CSS 移入独立 `.css` 文件，用 Vite 的 `?inline` 导入（`import styles from './content.css?inline'`），既保留现在"一次注入、无额外网络请求"的性质，又让 CSS 进入正常的压缩/校验链路（当前 CSS 嵌在 TS 模板里，会被当作字符串处理，压缩器无法优化）。
2. 用 `CSSStyleSheet` 共享解析结果：`adoptedStyleSheets` 支持同一 `CSSStyleSheet` 实例被多个 shadow root 采用。`pinnedHost` 与主 host 之间、以及**同一页面内多次创建**（`ensurePinnedHost` 已有复用，但 llm 面板是独立模板）可共享。
3. LLM 面板延迟创建：`llmDock` 的标记与样式在首次 `setLlmDockVisible(true)` 或首次展开时才注入。默认关闭的用户因此完全不付这份成本。

**理由与收益**：约 39 KB 的标记/样式解析 + 25 KB CSS 的应用在每个标签页、每个 iframe（当前未开 `all_frames`，暂为单帧）各发生一次。延迟创建对默认配置用户是纯收益；`?inline` + 压缩预计可减少 20–30% 的 CSS 字节。改动集中在两处模板，不触及逻辑。

### P4（中）大纲渲染是"全量重建 + 每个节点独立布局"

**证据**
- `content/index.ts:1244-1328`（`renderNotes`，options 侧对应 `736-785`）：`outlineList.replaceChildren()` 后整表重建。
- 每行 `noteDepth(id, ...)` 各调用两次（`1282`、`1284`），每次都是沿 `parentId` 向上遍历。
- 搜索计数（`1262`）对全部节点做 `filter` 且每项调用 `isNoteDescendant`（O(深度)）。
- `noteSubtreeHasMatch`（`1192-1200`）每层 `new Set(trail)` 复制，整体 O(n×深度) 次集合分配。
- 每行末尾调一次 `resizeNoteInput`（`1317`）→ `input.style.height = 'auto'` 后读 `scrollHeight`，即**每行一次强制布局**。

**建议**
1. `visibleNoteIds` / `noteSubtreeHasMatch` 改为一次自顶向下遍历并携带深度，同时输出 `ids`、`depthById`、`matchCount`，把三次遍历合并为一次。
2. `resizeNoteInput` 的逐行调用改为在一个 DocumentFragment 组装完成后统一执行（或用 `rows` 预估 + 仅在内容超长时精算）。
3. 中期：行级增量更新（按 `data-note-id` 复用已有行，只更新变化节点），或引入 keyed diff。不必一次做到。
4. 顺手：`getAvailableEngines`（`1824`）与 `getPinnedEntries`（`2125`）里 `ordered.some(item => item.id === id)` 是 O(n²)；条目数少（≤20）影响有限，但换成 `Set` 是零成本改动。

**理由与收益**：当前节点规模下可能感知不强，但大纲的定位是"无限层级笔记"，节点数会随使用增长；且"每次输入触发的操作都可能引发全量重建 + 每行一次布局"这个模式，在几百节点时会明显卡顿。第 1、2 项不改变结构即可把渲染成本降到接近线性且无布局抖动。

### P5（中）笔记整体作为单一存储键读写，跨标签同步成本随节点数放大

**证据**
- 写入：`content/index.ts:1051-1057` `chrome.storage.local.set({ [NOTES_KEY]: notesState })` —— 每次都写整份文档；由 350 ms 防抖的 `scheduleNotesSave`（`1059-1062`）触发。
- 读取侧：`content/index.ts:1119-1133` 与 `options/main.ts:602-619` 在收到 `storage.onChanged` 后，**先** `normalizeNotes(incoming)`（全量遍历 + 重建树），**再**用 `JSON.stringify` 比对签名决定是否跳过。

**问题**：任一标签页保存一次，所有其他标签页与设置页都会执行一次"全量 normalize + 全量 stringify"。即成本 ≈ 节点数 × 打开的标签页数，每次输入停顿都发生。

**建议**
1. 加一道基于版本号的短路：两处 `onChanged` 回调开头加
   ```ts
   const incomingUpdated = Number(incoming?.updatedAt) || 0;
   if (incomingUpdated && incomingUpdated === Number(notesState.updatedAt)) return;
   ```
   自我写入引发的回声即可整段跳过，不必 normalize、不必 stringify。
2. 写入侧改为携带 `expectedRevision`，或按节点分片存储（`notes/<id>`），把单次写入体积从 O(全量) 降到 O(单节点)。

**理由与收益**：第 1 项是 2 行改动，直接消除"自己写、自己被唤醒"这一最常见的路径；第 2 项是把成本从 O(n) 降到 O(1) 的结构性解法，适合在节点规模上升后择机做。附注：`notesState.updatedAt = Date.now()` 位于 `writeNotesStorage` 内（`1054`），时间戳单调递增的性质让该短路是安全的。

## 三、兼容性与正确性

### C1（高）`chrome.storage.sync` 单键 8 KB 配额与自定义图标冲突，失败静默

**证据**
- 图标经 `localFileToIconUrl`（`options/main.ts:1432-1461`）压缩为 32×32 后 `toDataURL('image/webp', 0.78)`，作为 `source.iconUrl` 存入搜索源对象。
- 搜索源数组整体作为**一个** `sync` 键写入：`saveGeneral`（`options/main.ts:454-463`）写入 `sources: settings.general.sources`。
- `saveGeneral` / `savePinned` / `saveHistory`（`455` / `464` / `473`）**均未检查 `chrome.runtime.lastError`**，回调里直接 `showSaved(...)`。

**问题**：`chrome.storage.sync` 的 `QUOTA_BYTES_PER_ITEM` 为 8192。17 个内置源已占约 3–4 KB，两个图标各 1.5–3 KB 即可越界 → 整个 `sources` 键写入失败 → UI 仍然显示"已保存"，用户下次打开发现改动没了。这是静默数据丢失。

**建议**
1. 立刻：给三个保存函数补 `chrome.runtime.lastError` 检查，失败时把 `saveStates[panel]` 文案改为「保存失败：超出同步配额」之类（`showSaved` 已是集中入口，扩展它即可）。
2. 结构性：图标不进 `sync`。改为 `storage.local` 下 `quickfind-icons` 的 `{ [sourceId]: dataUrl }`，搜索源里只留 `iconKey`；渲染时一次性读取本地图标表并注入。这样也给图标留出 `local` 的 5 MB（unlimitedStorage 之外）空间。
3. 至少：图标也纳入 `cleanSource` 的体积校验，超限时明确报错而不是静默写坏。

**理由与收益**：这是本次评审中唯一"用户已经保存成功、实际已丢失"的缺陷类别。第 1 项成本极低（三处各一行），第 2 项一次性消除类型层面的配额风险。

### C2（高）浮层可见性仍依赖 `z-index: 2147483647` 硬顶

**证据**：`content/index.ts:256`（host，2147483647）、`357`（`.llm-dock`，2147483646）、`458`（`.note-drag-ghost`，2147483647）、`2183`（`pinnedHost`，2147483646）、`2215`（`.pinned-group-list`，2147483647）。

**问题**：项目历史上已确认真实站点上存在同值透明埋点层把浮层盖住的案例；同值情况下层序由 DOM 顺序决定，注入位置（`document.documentElement.append`，`3029`/`2569`）并不保证靠后。当前代码里 2147483647 被三个不同元素使用，本身就存在内部互相遮挡的可能。

**建议**
1. 迁移到 **popover API（top layer）**：top layer 不参与 z-index 竞争，是唯一在"页面能顶到 2147483647 且可加 `!important`"的前提下仍然可靠的方案。已知三个必踩点需逐项处理：① `[popover]` 的 UA 默认样式（`inset:0` / `margin:auto` / `border` / `padding` / `overflow:auto`）必须压掉；② 宿主尺寸为 0 收不到点击，必须显式撑开；③ 位置属性设在宿主上（子元素 `position:static` 时无效）。
2. 过渡方案：把 z-index 收敛为单一常量表（`Z = { host: …, dock: …, ghost: … }`），并加运行时自检——浮层显示后用 `document.elementsFromPoint()` 取堆叠链，若自身不在首位，则临时切到 popover 模式。

**理由与收益**：从"大多数站点可用"变成"结构上不可能被遮挡"。这是已记录在案的重复踩坑点，且影响的是扩展的主功能（选中即搜），优先级高。

### C3（中）`attachShadow({ mode: 'open' })`

**证据**：`content/index.ts:257`、`2184`。

**问题**：页面脚本可读取并改写浮层 DOM 与样式，既可能被站点样式/脚本干扰，也带来"注入内容被静默篡改"的风险面。

**建议**：改为 `closed`。注意 `isEditingPinnedQuery`（`2325-2328`）等依赖 `pinnedHost.shadowRoot.activeElement` / `shadow.activeElement` 的逻辑需要改为通过内部持有的 root 引用访问（代码里已有 `?? closedRoot.activeElement`）而非 `host.shadowRoot`。改动面约 6–8 处，集中在常驻栏与笔记面板。

**理由与收益**：隔离性提升，消除页面侧干扰面。定级为中而非高，是因为当前未观察到因此产生的实际缺陷。

### C4（中）LLM 请求无超时，失败时 UI 可能永久卡在"进行中"

**证据**：`entrypoints/background.ts:81-102` 与 `content/index.ts:891-902` 的 `fetch` 均无 `signal`；`llmRequestInFlight`（`content/index.ts:935`）在 `finally`（`955`）里复位，但只在 fetch 自身 settle 时才会走到；`sendLlmMessage`（`925`）以 `llmRequestInFlight` 为闸门。全项目无 `AbortController`。

**问题**：网络挂起（非拒绝）时 `llmRequestInFlight` 长期为 `true`，后续发送被静默忽略，状态点停在「正在思考…」。

**建议**：两处 `fetch` 加 `AbortController` + 30–60 s 超时，超时后走现有的 catch 分支（会把错误写进对话气泡，`952`，用户能看到原因）。background 侧同时把 `sendResponse` 置于 `finally` 保证必达。

**理由与收益**：把"永久卡死且无反馈"变为"60 秒后给出明确失败原因"，符合项目既定的"只解释数据（失败原因）"的反馈偏好。

### C5（中）Firefox 目标未验证，依赖版本过于前沿

**证据**
- `package.json:8-12` 提供 `dev:firefox` / `build:firefox`，但 README 的安装章节只覆盖 Chrome；`wxt.config.ts` 的 `manifest` 只按 MV3 形状书写（`host_permissions`），MV2 需要 `permissions` 承接。
- `background.ts:8` 已对 `chrome.storage.session` 缺失做了判断（MV2 安全）；但 `manifest.background.service_worker` 在 MV2 下需为 `scripts`，`build.mjs:56-57` 两分支都读了，属已考虑。
- 依赖：`@types/chrome ^0.2.9`、`typescript ^7.0.2`、`overrides.vite ^7`，均为较前沿的版本线。

**建议**：跑一次 `npm run build:firefox` 并实际加载验证（重点：`chrome.storage.session` 回退、`contextMenus`、`options_ui` 在 MV2 下的表现），把结论写进 README；依赖改为精确版本（lockfile 已提交），CI 使用 `npm ci` 保证可复现。

**理由与收益**：要么明确支持并验证，要么从 `package.json` 移除 Firefox 脚本，避免留下"看起来支持、实际没验过"的第三种状态。

> 注：`('google'|'baidu'|…)` 等站点选择器、`isPinnedSearchResults`（`1904-1918`）依赖各站点 URL 结构，属于天然会腐化的部分（站点改版即失效），但当前设计有"选择器可配置 + 命中失败静默降级"的兜底，不需要在本次评审中处理。

## 四、代码结构与可维护性

### S1（高）同一领域逻辑存在 2–3 份实现，且已产生行为分歧

用户明确的原则是"同一条规则只能有一处实现"，但当前大纲模块整体被复制了两份：

| 逻辑 | content | options | 当前分歧 |

## 六、需要你确认的两项

### 6.1 已实测存在的缺陷：面板内按 Esc 无法关闭

项目历史回归记录中，`Escape关闭成功=false` 在改动前后两个版本上均复现，属既有缺陷而非回归。但按代码路径推论应当成立：`content/index.ts:2870-2876` 在 `document` 上以 capture 注册了 Escape → `hideAll()`，而 `keepPanelSearchKeysInOverlay`（`1611-1618`）只对 ArrowLeft/Right/Space 做 `stopImmediatePropagation`，不拦截 Escape。

**建议**：优先做一次定向实测确认（需明确测的是"触发点可见但未打开面板"还是"面板已打开"两种状态），再定位。若确认失效，最可能的原因是 `panelOpen` 状态与 `trigger.classList.contains('visible')` 在 Shadow DOM 内的键击路径下取值不符合预期——这条排查线索比盲目试改更快。

### 6.2 常驻栏默认 `allSites: true`（全站出现）

`content/index.ts:173` 的默认配置是"所有站点都出现常驻栏"，这是刻意的产品决策（默认值即作者当前配置）。需要确认的是：这是面向新用户的预期体验，还是仅为自己使用？

若面向公开用户，建议把默认改为按站点白名单（选项页已有该开关和站点列表），把 `allSites` 作为用户主动开启的选项；同时 `host_permissions: ['<all_urls>']` 与 content script 的 `<all_urls>` 匹配是商店审核的重点关注项，收紧注入面（改用 `chrome.scripting.registerContentScripts` 按站点动态注册）可显著降低审核阻力。此项涉及产品定位，请确认后再动。
